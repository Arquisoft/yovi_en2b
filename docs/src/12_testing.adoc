[[section-testing]]
== Test Report

This chapter documents the testing strategy applied across the YOVI system, covering all layers of the application: the Rust game engine, the backend services, the frontend, and the system as a whole.
The goal is to provide traceability between quality goals (see section 1.2 <<Quality Goals>>) and the concrete tests that validate them, and to give a transparent account of coverage and load results.

=== Overview

The project follows a layered testing approach that mirrors the system's architecture.
Each service owns its own test suite, run in isolation with coverage reporting.
End-to-end acceptance tests drive the full stack through a real browser.
A separate load test exercises the interoperability API under concurrent load.

[options="header",cols="2,2,2,2"]
|===
|Layer |Scope |Tool |Execution

|**Unit tests**
|Individual functions, services, and components in isolation
|Vitest (TypeScript) · Rust `#[test]` / `#[tokio::test]`
|Every push to `master` and every pull request (GitHub Actions)

|**Integration tests**
|HTTP routes against a real database (MariaDB)
|Vitest with a containerised database
|Every push to `master` and every pull request (GitHub Actions)

|**Acceptance / E2E tests**
|Critical user journeys through a real browser
|Playwright + Cucumber (BDD)
|On demand; also runnable in CI via `test:e2e:ci`

|**Load tests**
|Throughput and latency of the interoperability API under concurrent traffic
|Gatling (Java DSL)
|Run manually against the production deployment; results are reported in section <<Load Tests>>
|===

All TypeScript/React test suites use **Vitest** and produce LCOV coverage reports that are aggregated in **SonarCloud** (`arquisoft/yovi_en2b`) for a unified quality gate.
The Rust crate uses **cargo-llvm-cov** to produce a compatible LCOV report.

=== Unit Tests

==== gamey — Rust Game Engine

The `gamey` crate contains the core game logic and the HTTP bot server.
Tests are written using Rust's built-in test framework and `tokio::test` for async handlers.
The test suite is split across three files:

[options="header",cols="2,1,3"]
|===
|File |Tests |Coverage area

|`tests/core_tests.rs`
|43
|Game initialisation, move sequencing, win detection, illegal-move rejection, resign/swap rules, YEN round-trip serialisation, file save/load, coordinate arithmetic, board rendering.

|`tests/cli_tests.rs`
|54
|CLI command parsing (`place`, `resign`, `save`, `load`, `help`, `exit`, display toggles), index validation, game mode display, and save/load round-trips.

|`tests/bot_server_tests.rs`
|38 async
|HTTP bot server: `/status` health endpoint, `/v1/ybot/choose/{bot_id}` with valid and invalid YEN payloads, unknown bot-id rejection, pie-rule endpoints, and error-response structure.
|===

.Notable test groups in `core_tests.rs`:
* **Initialisation** — verifies board size, total cells (triangular formula: `n*(n+1)/2`), initial player, and cell availability.
* **Win detection** — three-side connectivity for both players on size 2, 3, and 5 boards, plus single-cell instant-win edge case.
* **YEN serialisation** — full round-trip (encode then decode) for empty and partially filled boards; invalid layout strings are rejected with a clear error.
* **Coordinate arithmetic** — `index ↔ coordinates` round-trips, side-touching predicates, and corner cells that touch two sides.

The `game` service owns all session state and validates every move server-side.
Its test suite covers the HTTP routes, the game logic layer, and the WebSocket manager responsible for real-time online play.

[options="header",cols="2,3"]

=== Acceptance Tests (End-to-End)

Acceptance tests validate the most critical user journeys against the full running system: frontend, backend services, and database.
They are written in Gherkin (BDD style) using **Cucumber** (`@cucumber/cucumber`) and driven by a real Chromium browser via **Playwright**.

Three feature files are implemented:

[options="header",cols="2,4"]
|===
|Feature |Scenario

|`register.feature`
|**Successful registration** — a new visitor fills in the registration form with valid data, submits it, and sees the account-created confirmation message.

|`login.feature`
|**Successful login** — a registered user fills in the login form with valid credentials, submits it, and lands on the games page.

|`create-game.feature`
|**Create a PvE game** — a logged-in user clicks "Play Now" on Game Y, selects "vs Computer" mode, clicks "Start Game", and sees the game board rendered correctly.
|===

Step definitions are located in `webapp/test/e2e/steps/` (`auth.steps.mjs`, `game.steps.mjs`).
The test environment starts the React dev server (port 3000), the `users` service (port 3001), and the `game` service (port 5000) in parallel before the Cucumber runner executes.

.Running E2E tests locally:
[source,bash]
----
# Install Playwright browsers (once)
npm --prefix webapp run test:e2e:install-browsers

# Start services and run all feature files
npm --prefix webapp run test:e2e
----

=== Load Tests

Load testing targets the **interoperability API** (`POST /interop/games/play`), which is the most computationally intensive public endpoint — it forwards board states to the Rust engine and waits for a move.
Tests are implemented with **Gatling** (Java DSL) in `loadtest/gatling/simulations/InteropSimulation.java`.

==== Simulation Design

The simulation runs for a maximum of **3 minutes** and injects virtual users (VUs) in a ramp to reach the following peak concurrency:

[options="header",cols="1,2,2,2"]
|===
|Scenario |Bot strategy |Peak VUs |Board sizes tested

|A · InteropOverhead
|`random_bot` (no minimax)
|5
|size 4 (empty and mid-game)

|B · FastBot
|`fast_bot` (500 ms minimax budget)
|3
|sizes 5 and 6

|C · SmartBot
|`smart_bot` (3 000 ms minimax budget)
|2
|sizes 4, 6, and 9 (absolute worst-case)

|D · DefaultFallback
|No `bot_id` sent
|3
|sizes 4 and 9

|E · HealthProbe
|`GET /interop/health` every 2 s
|1
|N/A
|===

**Peak total: 14 concurrent virtual users.**

The simulation distinguishes between successful engine responses (`200`) and overload rejections (`503`) by labelling Gatling groups with the HTTP status of the previous iteration (e.g. `SmartBot_200`, `SmartBot_503`).
This makes it possible to read the p95 latency of real engine computations separately from fast rejection responses in the HTML report.

==== Acceptance Criterion

The simulation asserts that the health-probe scenario (`GET /health`) has **0% failed requests**.
Play requests accept `200` or `503` responses; the distribution between them is the key finding: a high `503` rate indicates that the engine is saturated under the given concurrency.

==== Findings

Under the tested load (14 VUs peak, 3-minute soak) the health probe never failed.
The `SmartBot` scenario (2 VUs, size-9 boards) produced the highest latency and the greatest share of `503` overload responses, consistent with the `3 000 ms` compute budget per move.
The `random_bot` and `fast_bot` scenarios completed well within their respective latency budgets at the tested concurrency.
Full per-scenario percentile results are available in the Gatling HTML report located in `loadtest/loadtests-results/`.

Every TypeScript/React service generates a **LCOV** coverage report during the CI run.

=== CI Integration

All unit and integration test suites run automatically in **GitHub Actions** on every push to `master` and on every opened or updated pull request.
The workflow (`.github/workflows/build.yml`) performs the following steps:

. Install Node.js 22 and the Rust stable toolchain.
. Install dependencies for all four TypeScript packages (`webapp`, `users`, `game`, `interop`).
. Spin up a **MariaDB 11.4** service container (used by `users` and `game` integration tests).
. Run `vitest run --coverage` for each TypeScript package.
. Install `cargo-llvm-cov` and generate the Rust coverage report.
. Normalise LCOV paths and upload all reports to **SonarCloud** for analysis.

A failed test in any service fails the workflow, blocking the merge of the pull request.
